설계 시 고려 했던 사항

스프링 시큐리티와 jwt 토큰 사용

세션 방식의 경우 로그인 정보를 서버의 메모리에 저장하면 회원이 늘어날수록 서버의 부담이 커지기 때문에 jwt 토큰 방식의 로그인을 통해 서버의 무상태를 유지했습니다.
또한 access token의 유효시간을 짧게 두어 xss공격을 당했을 때 탈취 당해도 피해를 최소화 하도록 했습니다.
새로고침 시 로그인을 했음에도 access token이 없어져 로그인이 풀리는 것을 막기 위해 프론트에서 useEffect를 통해, 화면 최초 마운트 시 refresh token을 보내 access token을 재발급 받도록 처리했습니다.
httponly로 쿠키에 담아둔 refresh token에 대한 csrf 공격을 막기 위해, [SameSite=Lax] 옵션을 설정했습니다.

엔티티간 연관관계

데이터의 객체 그래프 탐색을 위해 연관관계를 설정했습니다.
join의 경우 단건은 문제가 없지만 다건의 경우 지연로딩의 N+1문제를 막기 위해 fetch join을 설정했습니다.
혹여나 놓치는 만약의 경우에 대비해 default_batch_fetch_size 옵션을 application.yml에 설정했습니다.
게시판과 댓글의 경우 게시판이 삭제될 경우 댓글도 삭제되어야 합니다. 이를 위해 CascadeType.REMOVE, orphanRemoval = true 옵션을 설정했습니다.
통계 데이터 조회 와 같이 특정 엔티티에 종속되지않는 데이터구조의 경우 dto projection을 통해 해결했습니다.

검증 및 예외처리

프론트에서의 검증을 위해 React-hook-form을 사용했습니다.
백엔드에서의 검증을 위해 @Valid 어노테이션을 사용했습니다.
@Valid와 같은 검증 예외 뿐만 아니라 백엔드 전반의 예외처리를 위해 @ControllerAdvice를 사용 및 apiResponse 클래스를 만들어 응답을 규격화 했습니다.

Zustand 및 TanStack Query

로그인 정보와 같이 프론트엔드에서 유지하고 있어야하는 정보를 위해 Zustand를 사용했습니다.
이미 사용자가 봤던 화면이라면 사용자의 빠른 경험과 백엔드의 부하를 줄이기 위해 tanstack query를 이용해 캐싱 처리를 했습니다.
거주지역 목록이나 직업정보 목록 같이 오래 변하지 않는 데이터 들의 경우를 제외하고, 사용자로 인해 데이터가 수시로 변할수 있는 부분들에 대해선 캐싱 처리를 하되, 변화가 일어날 수 있는 로직에 대해서 캐시 무효화 처리를 통해 변경된 데이터를 새로 불러올 수 있도록 했습니다.

트러블 슈팅

React-Spring 비동기 통신 시 CORS(Cross-Origin Resource Sharing) 에러

현상: 프론트엔드(GitHub Pages 환경)에서 백엔드 API 서버로 Ajax 요청을 보낼 때 브라우저 보안 정책으로 인해 요청이 차단되는 문제 발생.

원인 분석: 브라우저는 기본적으로 다른 도메인(Origin) 간의 자원 공유를 제한합니다. 백엔드 Spring Boot 설정에서 특정 도메인에 대한 접근 권한을 명시적으로 열어줘야하는데 스프링 시큐리티가 있을 경우 시큐리티에서의 cors설정이 최우선이기 때문에 WebMvcConfigurer를 구현한 WebConfig에서 이를 설정해도 통신이 되지 않는게 원인이었습니다.

해결 방법: WebMvcConfigurer에 있던 cors 설정을 시큐리티로 옮겨서 설정해주었습니다. http.cors(cors -> cors.configurationSource(corsConfigurationSource())) // cors

페이지에 처음 들어온 사용자의 개발자 도구 콘솔에 토큰 인증 401 예외가 뜨는 문제

현상: 페이지에 사용자가 처음 들어온경우 이거나, 로그인을 안하고 새로고침을 할 경우 인증되지 않았다는 401 예외가 개발자 도구에 나타나는 문제

원인 분석: 새로고침 시 로그인한 사용자의 액세스토큰이 사라져서 로그인이 풀리는 것을 막기 위해, 최상단 App.tsx에서 새로고침 시 화면이 마운트 될 때마다 refresh token을 서버로 보내 access token을 가져오는 로직이 있습니다. 해당 로직이 로그인 시에는 문제없이 작동하지만, 로그인 하지 않았을때는 refresh token이 없어서 발생하는 예외 였습니다.

해결 방법: 백엔드 입장에서 봤을때는 예외가 맞지만, 비즈니스 적으로 봤을때는 문제가 아닌 케이스라 생각했습니다. 컨트롤러에서 요청을 받았을때 다음 로직으로 넘어가기 전에 refresh token을 검사해서 null이라면 200 응답을 프론트로 보내도록 했습니다.

Supabase jdbc 연결방식 ipv4 문제

현상: Supabase db에 붙기 위해 백엔드에서 direct connection 주소(db.xxxxxxxx.supabase.co:5432)로 요청 시 에러가 발생하는 문제

원인 분석: direct connection의 경우는 db에 직접 붙는 것이 아닌 Supabase api에 요청을 보내는 주소입니다.

해결 방법: 백엔드는 api로 요청을 보내는 것이 아닌 Supabase 내부 PostgreSQL db엔진과 포트로 직접 통신해야 합니다. 이를 위해 application-prod.yml에서 direct connection 방식이 아닌 Session pooler 방식으로 연결설정을 수정했습니다.
